# Stock sale transaction and request replay

The `/api/stock/sell` successful response remains `{success:true,sale}`. The Phone transition, Sale snapshot, essential AuditLog, and optional request receipt now commit in one MongoDB transaction. There is no best-effort rollback or nontransactional fallback. A replica set or transaction-capable sharded cluster is required; a standalone server returns 503 without modifying stock. Production topology has not been contacted or verified.

`Idempotency-Key` is an optional header of 8–128 ASCII letters, digits, hyphens, or underscores. Within the authenticated tenant, the same key and normalized sale/role/shop intent return the original acknowledgment. A conflicting intent returns 409. Concurrent use is resolved by transaction conflict handling and the receipt collection's built-in unique `_id`; no automatic index migration is needed for receipts. Reads and writes inside transactions are sequential and explicitly receive the session.

The current sale form creates a UUID per intent (or 128 cryptographically random bits on HTTP browsers without `randomUUID`) and retains it in memory after an ambiguous response. It reuses it on an unchanged retry and rotates it when tenant/role/shop/payload changes. A response clears only its own request key and unchanged form; an older acknowledgment cannot clear a newer pending sale or paint its IMEI as sold. Replies from another signed-in context do not update the new context's UI. This does not promise request-key persistence across tab reloads or legacy installed clients. Legacy clients without a key still receive the conditional, atomic Phone/Sale transition, but do not receive arbitrary replay deduplication.

Prices must be positive, finite PKR amounts with at most two decimals; unsupported coercions and exponent-form strings are rejected. The transaction stores `buyPriceMinor`, `salePriceMinor`, and `profitMinor` as exact integer paisa while retaining rupee fields for existing consumers. Invalid legacy purchase costs cause a review conflict rather than being rounded or changed. New sale amounts that cannot round-trip through the legacy numeric response are rejected. Full report/currency migration remains T11–T13 work.

Duplicate legacy primary IMEIs are refused rather than choosing an arbitrary Phone. This is not a global uniqueness migration: concurrent stock creation, warehouse placement, transfers and full recovery remain planned tasks. Customer contact enrichment remains explicitly best-effort after the financial transaction; a contact failure does not undo an acknowledged sale.

The existing version-1 backup format gains an optional `stockOperations` extension, and restore retains sale minor-unit fields plus Phone/Sale attribution, notes and sale links. Before writes, restore validates receipt IDs/fingerprints/timestamps, exact sale snapshot fields and their referenced existing/incoming sales, and conflicting repeated receipt or sale IDs. Existing receipt outcomes are not overwritten. Replay also checks the stored outcome against the submitted intent rather than trusting a hash and arbitrary object alone. Empty-target round-trip testing verifies replay preservation, subsequent reversal and replay of its original acknowledgment. Receipts left orphaned by legacy sale deletion require review; restore does not silently invent their missing sale history. Older backends do not understand this extension and must not be used to restore files requiring replay history. Merge writes now run sequentially in a transaction, including expenses, shipments and dispatches; failures abort the whole merge rather than silently skipping records. This does **not** certify the legacy export as a consistent snapshot or the merge format as complete recovery. Those remain production-release gates in T10.

## Retained reversals and financial events

The warehouse continuation additionally joins sale/reversal to the tenant's shared primary-IMEI identity locks and rejects an IMEI simultaneously represented in HQ. Shop intake/edit/deletion and warehouse mutations use that authority too. Legacy inventory/history restores are now restricted to empty, identity-free inventory targets; new warehouse entry metadata requires versioned recovery. See `docs/WAREHOUSE-OPERATIONS.md` for this later, stricter recovery gate and the unchanged migration/complete-recovery limitations.

New sales retain `phoneId`, category/storage/color/secondary IMEI snapshots, and a matching Phone `currentSaleId`. Admin `DELETE /api/sales/:id` now reverses that specific sale in a transaction: the original Sale remains, reversal metadata and the essential audit commit with the conditional return to stock. Retrying an already reversed ID returns its stored reversal result without changing a later resale. Legacy unlinked sales require a unique active Sale and a matching sold Phone snapshot; ambiguous records return 409.

`DELETE /api/sales/by-imei/:imei` requires a captured `saleId` in its body. `GET /api/sales/current/:imei` captures the current active record before confirmation. Bulk `DELETE /api/sales` requires explicit `saleIds` (maximum 100 per transaction); the UI captures IDs before confirmation and batches larger selections. Old blind IMEI/clear requests return 409. Sold-phone deletion also returns 409; deleting available stock retains historical sales and commits its audit transactionally. No generic confirmation-dialog change is enabled by this slice.

`GET /api/sales` still returns active sales for admin callers. `ledger=true` returns original positive events plus dated negative reversals; optional `date=YYYY-MM-DD` bounds a Karachi business day. Shop callers may read only their authenticated shop's ledger. Seller attribution stays with `soldByShop`, with the legacy owning-shop fallback. Financial reports, CEO/model analytics, sidebar statistics, daily financial rows and sales-log screen/CSV/print now consume retained events. The shared browser/server rules use exact paisa totals and exclusive zoned period bounds; PKR formatting shows two decimal places. Daily rows retain each sold phone's cost total rather than multiplying the first phone's cost by quantity. Derived daily corrections are read-only, and saved monthly readers include their negative cost and units.

Reversals post on their Karachi execution date. Period close/reopen/revision enforcement and historical physical opening balances remain T12: this slice does not claim closed-period enforcement. Existing saved daily rows also need the planned reconciliation; they are not rewritten automatically. Full cross-view reconciliation, faithful general CSV escaping and complete recovery are still pending.

Backup exports retain the original sale, reversal metadata and original request receipt. Until versioned accounting recovery is implemented, merge restore rejects either incoming retained corrections or a target with retained corrections (409 before writes), preventing old backups from silently rewinding a return. Such exports must be preserved for the future accounting recovery workflow; there is currently no supported merge import for them. This is an explicit release gate, not a complete recovery implementation.

## Read-only preflight

```powershell
npm run inventory:check -- --client-id CLIENT_ID
```

Set `MONGO_URI` explicitly before invoking it; the command does not load `.env`. It connects only to that supplied target, verifies the client exists, reads inventory/cost/sale-state projections, prints a report, and disconnects. It never repairs records, creates/drops indexes, or applies a migration. This command was exercised only on disposable local fixtures during implementation.

Exit 0 means none of the implemented checks found an issue; exit 2 means reported conflicts require review; exit 1 means invalid invocation or failure. Checks cover primary IMEI format/duplicates, HQ/shop overlap, purchase-cost precision/range, and basic legacy Phone/Sale count consistency. It is not a complete financial reconciliation, migration approval, or proof that all stock writers enforce uniqueness. Buyer names and contact numbers are excluded from the report.

Unit and real database regression coverage includes concurrent sales, simultaneous replay/conflicting-key races, rollback after Sale/Audit failures, invalid prices, decimal profit, legacy duplicates, lost acknowledgment through the actual browser sale function and HTTP route, read-only preflight, standalone refusal, and backup restoration into another synthetic tenant. Browser code uses DOM stubs for these checks; physical browser/Android acceptance remains separate.
