# Warehouse movements and primary IMEI authority

Warehouse receiving, dispatch and removal now commit inventory, retained movement history, essential audit and optional replay receipt in one transaction. Shared `InventoryIdentity` documents use built-in unique `_id` values for primary IMEIs. Cooperating stock intake, edits, sale, reversal and deletion writers take the same locks; warehouse writes additionally serialize on the reserved `@hq` key. Initial lock-upsert conflicts retry transactionally. There is no nontransactional fallback.

No production reconciliation, index migration or data movement was run. Legacy duplicate HQ documents and conflicting HQ/shop placement fail closed. The growing HQ array is intentionally retained until a verified migration can replace it: updates use transactional push/pull rather than whole-array read/replace writes. Disjoint HQ operations can retry on the shared document; this removes lost updates but does not claim to remove singleton scaling or establish production throughput.

## Captured-entry protocol

- `GET /api/hqstock` exposes `entryId` on each item. New receipts persist a random UUID; legacy items get a deterministic hash projection without a read-time write. Ambiguous duplicate entries require reconciliation.
- `POST /api/shipments` accepts 1–100 primary-IMEI items, a real business date, optional supplier/reference and bounded metadata. Primary/secondary IMEIs must be exact strings of 15 digits. Costs use exact two-decimal PKR parsing; malformed/mixed quantity payloads fail instead of recording phantom inventory. Shipment items are canonical persisted snapshots with entry IDs and execution timestamps.
- `POST /api/dispatches` accepts captured `{imei, entryId}` selections plus date, destination shop and optional note. Stored HQ data supplies the cost and metadata; client replacements are ignored. Each selected entry must still match, and no shop Phone may already carry the IMEI. Phone insertion, HQ removal, retained Dispatch and audit commit together. Legacy recorded `costPerUnit` is preserved through a canonical buy-price snapshot; an unknown or malformed stored cost causes a review conflict, never an invented zero.
- `DELETE /api/hqstock/:imei` requires a captured `entryId`. A retry cannot remove a later receipt with a different token. Invalid/stale selections return 409 without moving anything.
- Whole-array `PUT /api/hqstock`, index-based removal and deletion of Shipment/Dispatch history return 409. These adapters preserve a clear response for older callers while preventing blind replacement, positional deletion and loss of movement evidence. The current UI displays retained history rather than delete-history controls.

Optional `Idempotency-Key` is 8–128 ASCII letters, digits, hyphens or underscores. The same tenant key and normalized warehouse intent return the original outcome; changed intent conflicts. Replayed movement snapshots must also match their retained Shipment/Dispatch document. A committed receipt/dispatch is not applied again. Old clients without keys retain transaction/location invariants but do not receive arbitrary response-loss replay. Old dispatch clients that omit entry IDs must be updated before they can dispatch; physical APK compatibility is still a release gate.

## Other writers and recovery fence

Shop intake now validates its location/cost and commits its audit with the new Phone under the shared IMEI lock. HQ intake uses the warehouse receiving workflow; unassigned Phone placement is rejected. Stock edits and available-stock shop transfers lock affected IMEIs and audit previous values/changes. Sold ownership or cost cannot be changed before reversal. This is not a new shop-to-HQ transfer UI or permission model. Sale/reversal retain their existing acknowledgment/history contracts while joining the shared authority.

The old `/restore` format cannot bypass these writers. After receipt-history validation, any inventory or shipment/dispatch import is refused if the target has inventory identities or physical/sale records. A legacy empty-target import checks primary IMEI shape and duplicate/cross-location placement, then takes the same locks in its transaction. Incoming warehouse entry metadata requires complete versioned recovery and is refused by the legacy path. A history-only payload is also fenced. Other legacy recovery validation remains incomplete; empty-target insertion is not proof of accounting consistency or recovery readiness.

Complete snapshot exports, manifests, all collection coverage, operation/identity recovery, validated replacement and migration fencing remain T10/T07. The legacy backup omits InventoryOperation and InventoryIdentity and must not be described as a complete recovery file. This continuation deliberately narrows legacy merge behavior rather than silently rewinding active inventory.

## Browser behavior and remaining gates

Receive/dispatch/removal use bounded pending-request slots and the shared keyed-request helper also used by products. Unknown responses retain keys and queued data. Only the current request in the captured tenant/shop/modal generation may clear matching form data or refresh the view. Dispatch action handlers keep metadata out of inline JavaScript, sending only selected identities. Malformed legacy IMEIs remain text without executable removal actions. Updated receive/dispatch fields have linked labels; broader dialog/focus/accessibility work remains pending.

Generic destructive confirmations remain gated until the other workflows and recovery tests are complete. Per-IMEI HQ storage migration, dedicated warehouse/shop transfer workflows, bulk queues beyond 100 items, fully bounded reads/exports, scale benchmarks, full recovery and physical-browser/Android acceptance are not certified by this slice. Secondary-IMEI global uniqueness and raw/manual/old-process database writers also require the planned reconciliation and fencing.

Tests run only against disposable loopback replica sets and browser VM fixtures. They cover overlapping/disjoint dispatches, concurrent receipts and shop intake, duplicate/corrupt payloads, captured replay after re-receipt, audit/partial-insert rollback, authoritative metadata/cost, sold location conflicts, edit constraints, corrupted outcomes, restore bypasses and read-only preflight. The sale race test now synchronizes two available snapshots immediately before the identity lock write; putting its barrier after serialization would deadlock the harness. No hosted service or production data is involved.
