# Contact and product paging

The web contact and product screens now load 50 records per page through additive `/api/v2/customers` and `/api/v2/products` endpoints. Both return `{items,total,nextCursor,hasMore}`, with a 1–100 limit. Newest ObjectId comes first. The UI labels page counts and matching counts separately and replaces rows on Previous/Next rather than accumulating all records. The old name-sorted array endpoints remain unchanged for existing clients.

Contacts remain administrator-only. Product shop sessions remain restricted to their authenticated shop; admin ALL includes all product ownership, including legacy unassigned entries. Product filters support configured `shop`, literal name search `q` and `availability=all|available|empty` (positive/zero quantity). Contacts search name, phone and email. Search is bounded to 80 characters/eight literal terms. Unknown/scalar-invalid filters fail explicitly; product search is debounced by 250 ms, contacts by 300 ms.

The shared document reader now serves stock, contacts and products. It uses explicit projections, lean rows, descending immutable ID cursors, per-response snapshot count/size/data reads and a 10-second query budget. Cursors bind resource, account, role/authenticated shop, configured shops and filters. Product revisions retain their existing contract, with legacy missing revisions presented as zero. No mutation/replay or accounting contract changed.

Traversal is anchored and live, as described in STOCK-PAGING.md: normal newer IDs wait for refresh, deletions disappear, updates/restored older IDs can change membership and Previous is live. It is not a retained cross-request database snapshot. The switch from name sorting to newest-first in the new screens is explicit; the old arrays keep their original order.

`/api/v2/customers/export` and `/api/v2/products/export` return `{items,total,complete:true}` only for the complete matching snapshot within 5,000 records and 8 MiB. Larger results return 413 without partial success. Database-side BSON size checking precedes Node materialization; final serialized bytes are also checked. Size checks measure the permitted output projection before document fetching, with a separate final JSON byte check. Stock now shares this reader and retains its prior response and limits.

Contact Print all matches requests the full filtered export. Product CSV all matches does the same, includes original quantity/cost/revision and quotes fields. Formula-leading product text, including whitespace/control-prefixed formulas in names or notes, is emitted as literal spreadsheet text; numeric quantities/prices remain numeric values. This protection applies to the new product export, not a claim that every older export has been audited.

Both screens use one shared browser pager with account/filter/generation ownership, cursor validation and last-good data preservation. Failed requests do not replace cached rows with an empty list. Changed-scope re-renders stay hidden. Late export responses cannot output a different context. Contact forms bind account and record identity; contact deletion and product deletion confirmations check loaded-page/filter ownership. Product quantity editing keeps the captured record ID and expected revision; opening a stale shop page is refused.

Unit/VM and disposable-database checks cover both resources, legacy compatibility, search/availability/permissions, scoped cursors, complete output/projection/size limits, page failure/supersession, revision edits, confirmation ownership and formula-safe product CSV. Stock compatibility tests exercise the extracted shared reader. These are not physical browser/native/screen-reader acceptance or production query/latency benchmarks.

Contact server-side optimistic revisions/idempotency, broader modal/draft handling, large streaming export jobs, other list migrations, full legacy export hardening and production index/throughput work remain separate plan gates. No automatic repair, production index migration, client support cutoff or deployed change is performed.
