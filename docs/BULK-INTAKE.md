# Bulk intake

The browser saves shop stock through POST /api/v2/stock/intake in sequential packets of at most25 phones. Each item has one stable key and its own atomic identity/phone/audit/receipt transaction. Staff ownership comes from authentication. Partial results are explicit: saved, failed, unknown or pending. An 8-second budget stops starting further items; uncertain work pauses the remaining packet. One in-progress transaction can exceed that start budget.

Before any POST, the complete immutable job (up to500 phones, including all later packets) is persisted and read back. Unique job IDs prevent separate tabs from overwriting each other. A tab-scoped pointer supports reload; unfinished jobs can also be explicitly resumed from Batch. No credentials are stored. Storage failure prevents submission. Unknown or damaged proof retains the original keys/body and blocks queue edits. Confirmed failures stay editable; a corrected save gets fresh keys only after those outcomes are definite.

Progress stays in memory. Reload deliberately replays the original saved prefix using its existing keys, then continues the remainder. This uses extra requests during recovery but avoids competing durable progress writers. Replay acknowledges the original intake after later editing, selling or deletion and never restocks that phone. All responses are checked against packet keys and phone facts. Navigation/account/shop changes stop further packets and stale UI changes. Cancel closes the form; it does not erase an unresolved job.

Version3 business recovery still covers23 collections. The existing InventoryOperation collection stores the typed stock_intake receipt. Its full original snapshot/fingerprint must match exactly one marked stock_add audit, and every marked audit must have a receipt. Original creation IDs must be unique; legitimate deletion/re-intake may reuse an IMEI with a new phone ID. Missing proof remains unresolved. Older backup/export/import paths refuse known intake evidence rather than dropping it.

Validation: focused UI tests cover complete-job durability, reload, multiple tabs, partial failure, malformed acknowledgements, storage and pointer failures, stale completion, duplicate clicks and cancellation/re-entry. A disposable real-API fixture commits25 phones, drops the response, reloads the browser scripts and safely finishes26 phones with26 receipts/audits. Full-suite results are recorded in FEATURE-EXECUTION.md.
